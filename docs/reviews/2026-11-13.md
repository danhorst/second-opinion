# Repository review — 2026-11-13

Follow-up: [provider hardening and current verification status](2026-11-13-hardening.md). The findings below record the initial review; several are addressed in that follow-up.

Scope: current working tree, specifications, provider adapters and conformance, CLI and skill installation, release workflow, and calling-agent instructions. Existing Codex adapter edits and its archive move were present before this review and preserved. This is a source review with local verification, not a new independent model review or a fresh provider conformance certification.

## Assessment

The small provider contract and explicit material assembly are good foundations for multiple front-ends. The repository is a working CLI, not yet the complete CLI/MCP/local-provider design described in its context. The main remaining risk is the gap between the strength of the cold-review and provenance guarantees and what the adapters and tests actually establish.

## Remaining findings and recommended order

### 1. Strengthen evidence for cold isolation before expanding the provider roster

`internal/provider/providertest/conform.go` tests a relative `secret.txt` reference while adapters run in an unrelated temporary directory. This proves that one relative lookup does not reach the caller's file; it does not demonstrate denial of an absolute path deliberately mentioned in material. The Codex adapter's read-only sandbox flag alone is not proof that reads are denied. Antigravity's invocation also has no explicit suppression of global configuration in the code, despite the global-context requirement in `openspec/specs/provider-conformance/spec.md`.

Add an absolute-path canary case, retain the positive-control gate, and exercise harness-global context using isolated test homes/configuration that preserve only explicitly selected authentication. Capture the installed binaries' actual capabilities before changing adapter flags. A negative model answer is observational evidence, not an exhaustive access-control proof. These gaps are not evidence that a leak occurred during this review.

### 2. Fail closed on invalid provider transport output

`internal/provider/codex/events.go` ignores `Scanner.Err()` after its 4 MiB line limit and skips malformed events. `codex.run` accepts the resulting string after exit zero, without distinguishing a valid empty response from a stream containing no recognized result. An oversized later event can leave stale earlier findings looking successful. The recursive message search also accepts message-shaped objects outside a validated final-result event.

Give transport parsing an error-bearing result and validate terminal success separately from empty findings. Add captured-event unit cases for oversize/truncation, no final result, and embedded message-shaped objects. Keep nonfatal item warnings valid. `claude.Review` likewise accepts any syntactically decodable JSON object without validating a result envelope type; `{}` or `null` can become an empty successful result. This work overlaps the existing Codex edits and was left separate.

### 3. Close the conformance requirements-to-tests gap

`checkCancellation` tests only an already-cancelled context, while the interface promises cancellation during an active review. `exec.CommandContext` controls the immediate process; descendant processes holding output pipes can outlive it or delay return. The new CLI timeout supplies a deadline but cannot itself fix adapter process-tree handling.

The shared suite checks populated provenance and a prompt hash, but cannot establish model identity simply from a nonempty string. It also does not independently exercise all the empty-result/unreachable-provider scenarios its spec names. Add explicit real-boundary cases for in-flight cancellation and unavailable providers; document model identity as observed, requested, or unknown in a future provenance revision.

### 4. Resolve large-input transport before promising repository-scale review

Claude and Antigravity embed all material in one command-line argument (`buildInvocation` in each adapter). They are subject to OS argument-size limits, irrespective of model context capacity. Assembly and all adapter outputs are fully buffered without a material/output budget. The local allocation improvement below does not solve either limit.

Investigate supported stdin/streaming transport against real binaries, or reject oversized material before launch with an actionable diagnostic. Preserve explicit material semantics and prove delivery with the positive control. Avoid silently truncating or splitting reviews: splitting changes the review context and needs a separate design.

### 5. Finish the transport surface independently of heuristic findings parsing

MCP and Ollama remain absent, and `openspec/changes/findings-envelope` is still an unimplemented proposal. MCP can expose raw text and provenance without requiring a heuristic parser to be authoritative; the new CLI JSON deliberately establishes no finding count or ranking. Revisit whether parsing must block MCP at all. Ollama is the outstanding local-material route, so no currently registered provider should be presented as a local-only review option.

Stdin targets, staged-only review, and explicit supporting files alongside a diff are useful later ergonomics work. The existing mutually exclusive file/diff modes remain unchanged; the skill now makes the untracked-file exclusion explicit.

The skill installer still writes Codex custom prompts, not the canonical skill document with frontmatter to a native skill directory. Before migrating it, verify supported discovery locations against the target harness version and define an idempotent migration. Do not silently delete existing installed files.

## Performance measurement

Command: `go test ./internal/review -run '^$' -bench BenchmarkFromFiles -benchtime=300ms -count=2`, Go toolchain from this repository, Apple M4, warm local filesystem. Ranges are two short samples, not statistical confidence intervals or an end-to-end service benchmark.

| Input | Before allocated bytes/op | After allocated bytes/op | Before time/op | After time/op |
| --- | ---: | ---: | ---: | ---: |
| 1 MiB | ~4.22 MB | ~3.17 MB | 195–202 µs | 177–178 µs |
| 10 MiB | ~41.97 MB | ~31.48 MB | 1.78–1.92 ms | 1.44–1.49 ms |

The allocation reduction is one input-sized string, approximately 25% of total allocated bytes here. Reviewer latency, provider throughput, and memory use in provider subprocesses were not measured. No caching or parallel review mechanism was added without evidence of benefit or a material-identity design.
